# 用户流程设计：从需求到交付，以及交付后的调整

> 状态：设计已确认（2026-10-30）。实现分两步：
> - 第一版（本次）：对话入口、需求分析、架构方案选择（一个或多个方案）、按顺序执行、交付报告、`help`、`team`。
> - 第二版：交付后的调整（A/B/C/D 分类与执行）。
>
> 依据：团队公约第 3、12、13 节；手册第 3.4 节（返工回路）。本文只写用户看得到的流程，内部规则以公约为准。
>
> 已确认的默认值：B 类调整默认改原 REQ；D 类重构默认开新分支，执行前由你确认范围；A 类小修修完告知即可，无需确认。

## 一、用户只需要知道的事

1. 在项目目录里运行 `agentteam`，进入对话。对话的对象是团队（CLI 负责调度各角色）。
2. 你用自然语言提需求、确认方案、提出修改意见。
3. 团队在后台分工执行。只有一个地方会停下来等你：**选择架构方案**（可以是一个或多个方案）。
4. 需要你选择的事项，团队会列出选项，用序号、字母或上下键确认即可。
5. 完成后，团队给出交付报告，路径在 `docs/delivery/`。

你不需要知道角色之间怎么传话、门禁编号是什么、任务卡怎么写。这些都在过程记录里，需要时可查。

## 二、正常交付流程

```
你        ：提出需求
团队      ：需求分析写 REQ-001.md，架构师给出 1 个或多个方案 → 写 ARCH-001-summary.md（一页摘要）→ 列出方案（G1.5）
你        ：选择方案（序号 / 字母 / 上下键），或写讨论意见（架构师据此修改方案，讨论不会当作新需求）
团队      ：按选定的方案拆任务卡，自动串行执行：原型 → 设计/契约 → 后端 → 前端 → 测试（G2–G5）
团队      ：验收通过 → 写交付报告 DELIVERY-001.md
你        ：阅读报告，接受，或提出调整（见第三节）
```

执行过程中，团队只在三种情况下打扰你：

| 情况 | 团队怎么说 |
|---|---|
| 需求有歧义，团队无法自行判断 | 列出两个理解，请你选一个 |
| 方案与已确认的需求冲突 | 说明冲突点，请你决定改哪一边 |
| 连续三轮返工仍未收敛 | 给出 2–3 个处理方案，请你裁决（会写入 ADR） |

## 三、交付后的调整：先分类，再执行

你对交付不满意时，直接在对话里说，例如"导出的 Excel 列顺序不对"。团队不会直接改代码，先判断属于哪一类，并告诉你：

| 类型 | 典型例子 | 处理方式 | 你的确认点 |
|---|---|---|---|
| **A. 缺陷修正** | 功能与需求一致，但表现不对：样式错位、文案错、某个按钮不工作 | 测试开 BUG 单，归属角色修复，回归后关闭。走缺陷回路（公约 12.5 节） | 无需确认，修完后告诉你改了什么 |
| **B. 需求调整** | 需求写漏了，或你改了主意：要加字段、改验收条件 | 需求分析修改 `REQ-NNN.md` 的变更记录；团队判断影响范围，从最早受影响的门禁重新走 | 确认变更内容与影响范围 |
| **C. 方案调整** | 技术栈不合适，或你想换架构 | 架构师出新方案 `ARCH-NNN+1`，你确认后写 ADR，技术栈档案版本升级（档案是你的资产，由你确认） | 选择新方案；确认是否迁移现有代码 |
| **D. 重构** | 功能要保留，但代码结构需要整体调整 | 视为新任务。团队开新任务卡，执行前请你确认范围；代码改动在独立分支进行（见第五节） | 确认范围，以及是否接受分支方式 |

判断规则：

- 能用"修一下"描述的，是 A。
- 需要改 REQ 里的某条需求或验收条件的，是 B。
- 需要换技术栈或架构的，是 C。
- 功能不变、只改内部结构的，是 D。
- 拿不准时，团队会问你，不会猜（公约 R5）。

## 四、调整的具体流程

以"导出 Excel 列顺序不对"为例（A 类）：

```
你    ：导出的 Excel 列顺序不对，应该是 订单号、客户、金额
团队  ：这是缺陷修正（A 类），REQ-001 的验收条件"列顺序"未满足。
        将开 BUG-001，归属后端开发。确认吗？
你    ：确认
团队  ：后端开发已修复（改动：src/export/excel.ts）。测试回归通过。
        已修复，改动已记入 docs/bugs/BUG-001.md。
```

以"加一个按客户筛选"为例（B 类）：

```
你    ：导出时要能按客户筛选
团队  ：这是需求调整（B 类），会改 REQ-001 并影响后端、前端、测试。
        影响范围：REQ-001 增加条目 REQ-001-A5；已通过的验收项 A1–A4 不受影响。
        需要从 G1 重新确认需求。确认吗？
你    ：确认
团队  ：REQ-001 已更新（变更记录第 2 条）。请确认新增条目 REQ-001-A5 的内容：…
你    ：确认
团队  ：开始执行 A5 相关任务，完成后生成 DELIVERY-002.md（与 DELIVERY-001 并存）。
```

以"换成 React"为例（C 类）：

```
你    ：前端能不能换成 React？
团队  ：这是方案调整（C 类）。架构师将出新方案 ARCH-002，与现有方案对比。
        注意：现有前端代码（约 N 个文件）需要迁移或重写，这一项由你决定。
架构师 ：ARCH-002-summary.md 已写好：方案 A 保留 Vue（不迁移）；方案 B 迁移到 React（预计 …）。请选择。
你    ：选 B
团队  ：已写 ADR-002，技术栈档案 stacks/xxx.md 版本升至 v2（需你确认档案改动）。
        迁移方式：新建分支 migrate/react，逐页迁移，旧代码保留到验收通过后再删。
```

## 五、重构与版本保护

- **所有代码改动都在任务分支上进行**（公约第 7 节：`task/T-NNN-描述`）。主分支只放通过验收的内容。
- **CLI 不会自动提交或合并**（公约 R6）。改动在分支上完成后，由你决定合并或放弃。
- 不满意时可以不合并，主分支保持不变。
- 已合并的功能要回退，用 `git revert`，历史保留，不改写。

## 六、交付报告的版本规则

- 每次交付（包括调整后的交付）生成一份新的 `DELIVERY-NNN.md`，**旧报告不改写**，便于追溯"当时交付了什么"。
- 新报告开头注明它替代或补充哪一份，例如"本报告补充 DELIVERY-001，新增条目 REQ-001-A5"。
- 报告只写用户关心的内容：做了什么、怎么用、还有什么限制、你做过哪些决定。

## 七、门禁如何重新进入

变更从最早受影响的门禁重新进入，不从头开始：

| 变更类型 | 重新进入 |
|---|---|
| A 缺陷修正 | 测试回归（G5） |
| B 需求调整 | G1（需求确认），之后按受影响范围进入 G2–G5 |
| C 方案调整 | G1.5（方案确认），之后迁移与实现 |
| D 重构 | G3（基座）起，重新走实现与测试 |

已通过的门禁不重复核对，除非变更影响到它。

## 八、防止无限返工

- 同一问题来回超过三轮仍未收敛，团队停下来，请你裁决并写入 ADR。
- 你也可以主动说"停止这个问题，按现状交付，记为遗留"。团队会把它写进交付报告的"已知限制"。

## 九、CLI 上的体现（计划）

| 你做的事 | 命令 |
|---|---|
| 提需求、提修改、确认方案 | `agentteam`（对话） |
| 查看当前进度与每个角色用的 agent | `agentteam team` |
| 查看全部需求、方案、交付版本 | `agentteam history` |
| 切换某个角色的 agent | `agentteam assign <角色> <agent>` |
| 查看帮助 | `agentteam help`（带快速开始） |

`dispatch` 保留为内部实现，不作为日常入口。

## 十、需要你确认的默认值

1. **B 类调整默认改原 REQ（加变更记录）**，还是默认新开 REQ？推荐：改原 REQ，这样 REQ 始终是一份完整文档。
2. **D 类重构默认开新分支**，并且执行前必须你确认范围。推荐：是。
3. **A 类小修是否需要你确认后才执行**？推荐：不需要，修完告诉你即可，因为它不改变需求。
