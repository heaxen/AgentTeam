# README · AI 开发团队落地文件使用说明

这套文件把你的一群独立 AI 会话组织成一支小型开发团队。共四类文件，分两层：

| 文件 | 层 | 作用 | 放哪 |
| --- | --- | --- | --- |
| `AGENTS.md` | 通用公约 | 所有角色会话的共同规章，不含任何具体技术栈 | 仓库根目录 |
| `AI开发团队角色与协作流程.md` | 通用公约 | 团队手册：设计原则、角色卡片、流程与门禁、契约规则、目录结构、分阶段启用 | 仓库根目录 |
| `prompts/*.md` | 通用公约 | 七个角色的会话开场说明，直接粘贴为会话第一条消息 | 建议复制到 `team/roles/` |
| `stacks/_template.md`、`stacks/<project>.md` | 技术栈档案 | 本项目用什么框架、代码放哪、跑什么命令、有哪些硬性禁令 | `stacks/`，每个项目一份 |

冲突裁定顺序：**公约的流程与禁止事项 > 本项目技术栈档案 > 手册中的示例与建议**。档案只能在"用什么技术、代码放哪、跑什么命令"上覆盖手册的通用建议；流程与禁止事项任何档案都改不了。

## 一、按顺序做这六步

### 第 1 步：把公约与手册放到仓库根目录

把 `AGENTS.md` 与 `AI开发团队角色与协作流程.md` 一起放到仓库根目录，与源码同级。角色会话靠相对路径读它们，文件不在根目录，开场说明里的路径就会失效。

顺手建好协作目录（这类目录全项目通用，与用什么技术无关；手册第 5 章有完整树）：

```
team/tasks/  team/roles/  stacks/
docs/requirements/  docs/prototype/  docs/design/  docs/api/
docs/frontend/  docs/backend/  docs/bugs/  docs/acceptance/  docs/decisions/  docs/changelog/
tests/cases/  tests/reports/  tests/smoke/
```

应用代码目录（前端、后端、组件、请求层、表结构脚本）**不在这里写死**，由下一步的档案定义。

### 第 2 步：为本项目填写技术栈档案

1. 复制 `stacks/_template.md` 为 `stacks/<project>.md`（短名小写，如 `nta.md`）。
2. 逐字段填「取值」与「证据来源」：取值写"选型 + 版本"，证据来源写具体出处（配置文件名、命令输出、行号）。没有证据的字段写「未确认」并登记到档案 §10，不要留空，不要写"应该""估计""通常"。
3. 必填的关键字段：§1「前端目录 `/` 后端目录」、§2「组件目录」「请求层落位与统一入口」、§3「接口契约的生成方式与产物」、§4「表结构变更方式」、§6「验证命令」、§7「硬性约定」。这几项空着，实现类角色无法开工。
4. 档案第一版由你确认后才可派活。未确认的档案只能用于做技术调研类任务。

**多项目时怎么复制**：每个项目复制一次模板、填一份档案，档案互不合并；角色会话也各自独立，**禁止跨项目共用会话**。若多个项目的团队文件放在同一处，用 `stacks/proj-a.md`、`stacks/proj-b.md` 区分；若某项目太大需与团队文件分仓，可把档案放该项目根目录，但必须在任务卡与角色开场里写明路径。

参考已填好的真实样本：`stacks/nta.md`。

### 第 3 步：通读手册

至少读这几处，其余当字典查：

- 第 0 节（两层结构与占位符）——先弄清"公约不写技术栈、一切事实来自档案"。
- 第 1.3 节（六条铁律）——决定日常行为的红线。
- 第 1.4 / 1.5 节（两层结构与拓展机制）——决定新项目、新栈、多项目怎么接。
- 第 3.2 / 3.3 节（串行并行 + G1–G5 门禁）——决定什么时候能让下一个角色开工。
- 第 4 章（契约规则）——决定前后端不吵架的前提。
- 第 7 章（分阶段启用）——决定第一批只开哪几个会话。

### 第 4 步：按 `prompts/` 建会话

每个角色一个**长期固定会话**，会话标题写死角色名。开场时把对应文件粘贴为第一条消息，**粘贴前先把文件里的 `<PROJECT_STACK_FILE>` 换成第 2 步的档案路径**（例如 `stacks/nta.md`），不留占位符。

| 开场说明 | 建议会话标题 | 复制到 |
| --- | --- | --- |
| `prompts/req-analyst.md` | `[角色] 需求与原型` | `team/roles/req-analyst.md` |
| `prompts/architect.md`（草稿） | `[角色] 架构师` | `team/roles/architect.md` |
| `prompts/frontend-dev.md` | `[角色] 前端开发` | `team/roles/frontend-dev.md` |
| `prompts/backend-dev.md` | `[角色] 后端开发` | `team/roles/backend-dev.md` |
| `prompts/qa.md` | `[角色] 测试` | `team/roles/qa.md` |

注意：

- 其余六个会话彼此不说话，一切跨角色沟通经 CLI 流程转达（写入 `docs/messages/`）。
- 复制到 `team/roles/` 后，以该副本为准；`prompts/` 只作母版留存。
- 每个会话的第一条消息里，档案路径必须是真实路径；角色发现档案缺失或关键字段为空时，会按公约停下来回传，不会自行猜技术栈。

### 第 5 步：第一阶段只开四个会话

按手册 7.2 的"最小可用团队"：

| 会话  | 角色   | 说明                                                          |
| --- | ---- | ----------------------------------------------------------- |
| 1   | 需求与原型 | 独立会话（需求文档与可点击原型由同一会话产出）                    |
| 2   | 前端开发 | 独立会话（含 UI 基座：视觉规范、设计 token、通用组件）             |
| 3   | 后端开发 | 独立会话                                                        |

此时**不开**测试会话。测试工作由你按 `REQ-NNN.md` 的验收条件手工点检，结果写 `docs/acceptance/AC-NNN.md`。这不是省掉验收，只是执行人暂时由你兼任。

第一个任务刻意选小：一个登录 + 一个列表页 + 一个接口。目标是跑通 G1→G5，不是把功能做全。

### 第 6 步：等验证信号出现，再逐个加会话

| 要加的会话 | 触发信号 | 依据 |
| --- | --- | --- |
| 测试 | 连续 2 个任务里，测试发现的缺陷 ≥ 50% 是你手工点检时漏掉的；或同一缺陷两次逃过验收 | 手册 7.1 P1 |

加会话时同步做一件事：把 `prompts/<role>.md` 复制到 `team/roles/` 并替换档案占位符。

信号没出现就别加。会话越多，门禁执行成本越高，而收益没到就是纯损耗。

## 二、每个任务的标准动作（速查）

| 谁 | 做什么 | 产出 |
| --- | --- | --- |
| CLI 流程 | 建任务卡（含"适用档案"路径），派活 | `team/tasks/T-NNN.md` |
| 角色 | 读公约 + 档案 + 任务卡 + 输入文件，干活，落盘，回传 7 字段 | 各自目录下的交付物 |
| 你 | 核对文件真实存在 + 逐条核对门禁（需要命令的按档案实跑） | 门禁结果记录 |
| 你 | 验收，写结论 | `docs/acceptance/AC-NNN.md` |
| CLI 流程 | 阶段结束汇总 | `docs/changelog/TEAM-NNN.md` |

三条最容易忘的日常规则：

1. 只写在会话里、没落盘的成果，视为不存在。
2. 前后端字段对不上时，以契约产物 `<CONTRACT_FILE>` 为准（路径见档案 §3「接口契约的生成方式与产物」）；契约本身有歧义，停手交你裁决。
3. 任何角色都不自动 `git commit` / `git push`，提交由你明确要求。

## 三、常见问题

| 问题 | 处理 |
| --- | --- |
| 某角色老是跑偏、越界 | 把 `AGENTS.md` 第 10 节"禁止事项"与开场说明第八节重新贴进该会话；仍跑偏就重开会话并附交接摘要（手册 6.5） |
| 角色在猜框架、猜目录 | 大概率是档案没填或没写路径。补档案、把档案路径写进开场说明；不要指望角色"自己判断" |
| 换了一个项目，发现角色按旧项目的栈干活 | 该会话是跨项目复用的。按公约，跨项目必须新建会话，不能共用 |
| 档案和代码对不上 | 记下来交用户确认，改档案（升版本 + 写变更记录）。角色不许自行改档案 |
| 会话上下文过长、开始记错约定 | 用交接摘要重开同角色会话，摘要只写文件里读不到的信息，其余给路径 |
| 门禁总是卡在同一条 | 说明该条不可执行或角色说明书没写清，改说明书，别硬扛 |
| 某个门禁从来没拦住过问题 | 直接删掉这条，流程变短才真正可执行（手册 7.3） |
| 想加需求管理工具 / CI | 现阶段不需要。先让"文件即状态 + 门禁"跑顺，工具是后面的事 |
